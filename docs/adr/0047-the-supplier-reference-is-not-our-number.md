# ADR 0047 — The supplier's reference is not our number

- **Status:** Accepted
- **Date:** 2026-08-28
- **Context:** Spec §13, §19. `bills.number` has carried two different things
  since Phase 2, and the constraint on it was wrong in both directions at once.
- **Builds on:** [ADR 0041](0041-the-document-you-raise-yourself.md),
  [ADR 0033](0033-books-that-check-themselves.md),
  [ADR 0045](0045-the-record-you-can-never-fix.md)

## Context

The bill composer has a field labelled **"Their reference"** with the
placeholder `INV-4471`. It writes into `bills.number`, which is also where this
system puts its own generated `BILL-1002`, and which is `UNIQUE (company_id,
number)`.

One column, two meanings, and the constraint fails both:

**It refuses what it should allow.** Two different suppliers both numbering an
invoice `INV-4471` is not a coincidence — it is how invoice numbering works.
The second bill hit a raw Postgres unique violation. And because `createBill`
threw a plain `Error`, `messageFor` returned the caller's fallback: the person
holding a real supplier invoice was told **"Something went wrong."** and left
with no way to enter it.

**It allows what it should refuse.** The same supplier's invoice entered twice
— once from the emailed PDF, once from the posted copy — was caught only if
somebody typed the reference both times. The field is optional, so the safe
path was the one nobody took, the two rows got different generated numbers, and
both got paid. Paying a supplier twice is the most expensive routine mistake in
small-business bookkeeping, and getting the second payment back is a favour
rather than a right.

## Decision 1: a reference identifies a document within a supplier

Everything else follows from that one sentence. `bills` now carries
`vendor_reference` (theirs, verbatim — it is a quotation) and `reference_key`
(normalised for comparison), with a **partial unique index on (company, vendor,
reference_key) where it is not null**. `number` goes back to being ours alone,
always generated.

Partial, because most bills carry no reference and null is not "the same as"
another null: a supplier who numbers nothing must not block the next unnumbered
bill from anybody.

`number` on existing rows is left exactly as it is. It appears in journal
memos, payment references and the audit trail, and rewriting a document's
number after the fact would make those point at nothing.

## Decision 2: refuse only what is certain

The costly wrong answer here is not "warning about a bill that turns out to be
fine" — that costs a click. It is **refusing a real supplier invoice**, which
leaves a business unable to record what arrived and its books wrong until
somebody fights the software.

So exactly one case is refused: the same supplier's same reference. That is not
a resemblance, it is the same document — a supplier does not issue two invoices
under one number, so one of the two was keyed wrong. It is not overridable,
because there is nothing for a person to know that the supplier's own numbering
has not already said.

Everything else warns and hands the decision back:

- same supplier, same amount, same day → warn
- same supplier, same amount, within a fortnight → warn
- same supplier, same amount, a month apart → **silent**, because that is rent,
  and a warning that fires every month is one nobody reads by the third
- both sides carry a reference and they differ → **silent**, because the
  supplier has already said these are two documents

That last rule came out of a test written before the rule was right: a builder
invoicing two sites for the same amount on the same day, under `INV-4471` and
`INV-4472`, was being warned about. Fixed in the module, not the test.

## Decision 3: the messages were always there

`createBill` and `recordPayment` threw plain `Error` — **thirty-three** of
them, every one a sentence written for a person: *"Record one payment per
currency"*, *"Retainage must be less than the bill total"*, *"Accounts Payable
account is missing from the chart"*. `messageFor` returns its caller's fallback
for anything that is not a `DomainError`, so all thirty-three reached the user
as *"Something went wrong."*

They are now `DocumentError`, which also carries an `overridable` flag. The
screen offering "do it anyway" and the rule deciding what may be done anyway
read the same field, so they cannot drift apart.

## Decision 4: the highest number, not the count

`nextDocumentNumber` counted rows. That is the same answer only while every
document was generated by it — and it never was, because the composer let
somebody type a number. A company with four typed documents got its next
generated one at 1005, and if any of those four was `BILL-1005` the insert
failed on a unique violation, reported as "Something went wrong."

Reading the highest number actually issued is right whatever else is in the
table. Two concurrent inserts still read the same maximum; the unique
constraint arbitrates, which is the rule everywhere in this system that two
people can act at once.

## Decision 5: find the ones already in there

A rule at the door protects a business from today onwards and does nothing for
the six months already in the books — which is where the duplicate that gets
paid twice actually is, because nothing has ever looked. `payables.duplicate_bills`
pairs them using the same pure verdict the composer uses, so the list cannot
disagree with the warning that would have stopped it.

It is a **position**, not a fault. Two bills for the same amount a week apart
is how a weekly delivery looks, and reporting a suspicion as a broken book is
how a check gets ignored. It says "somebody should look at these two", which is
true.

## Decision 6: two records for one supplier — found in the browser

Verification of this phase's own demo showed the supplier dropdown offering
**Delta Electrical twice**.

That is not cosmetic. The duplicate rule is keyed on the vendor, so a supplier
split across two records is invisible to it: the same invoice entered against
each reads as "two suppliers using the same number", which is the case this
phase deliberately allows. The check at the door was blind to exactly the
duplicate it exists to stop, and the pair finder never paired them either. A
split supplier is also its own problem — their balance, their aging and their
1099 total are each half right.

So `createCustomer` and `createVendor` now refuse a name already on the books.
Overridable, on the same reasoning as everything else here: there is more than
one "Smith & Sons", and refusing outright would leave somebody unable to record
a supplier who exists. The seed, which caused this one, now reuses the vendor it
already created.

## Consequences

- Two suppliers may use the same invoice number. This was impossible before.
- One supplier may not repeat their own, and the refusal names the bill it
  clashes with rather than saying "duplicate".
- Every refusal in the receivables module is now readable.
- The bill list shows the supplier's reference, which is the number anybody
  actually has to hand.
- A company migrating in keeps whatever `number` its old system used; the
  backfill treats anything not matching `BILL-nnnn` as the supplier's reference,
  which is what the field asked for.
- Nothing merges or deletes a suspected duplicate. Voiding the one that should
  not exist is a person's decision, and the other keeps its number.
